# Makunouchi 要件定義・設計

作成日: 2026-10-25
改訂日: 2026-11-07（`docs/requirements/` の資料を正として改訂）

> 要件の正は [`docs/requirements/`](../../requirements/README.md)（企画書・行動シナリオ・UI作成・手書きスケッチ）。この文書はそれを設計に落としたもので、食い違ったときは `docs/requirements/` を優先する。資料から判断できない点は「8. 未決事項」にまとめた。

## 1. 目的と背景

結婚式で参列者に楽しんでもらい、新郎新婦のことを知ってもらうための 4 択クイズシステム。参列者は自分のスマホから参加する。

- クイズは事前に作成でき、繰り返し使える（リハーサル回と本番回など）。
- 有料化や一般公開は考えていない。ただし、知り合いの範囲で使えるようにインターネット上には公開する。

**最も重要な品質**: 披露宴の最中に、アクセスの集中で画面が固まって進行が止まることが絶対に起きないこと。構成上の判断はすべてこれを最優先にする。

## 2. 利用者

| 利用者 | 使う画面 | やること |
|---|---|---|
| システム管理者 | 管理画面、各クラウドのコンソール | 主催者のアカウントを作る。Cloudflare と Cloud Run のログを確認する |
| 主催者（結婚式を開催する人） | 管理画面 | 問題と答えを作成・編集する。開催回を作る |
| 幹事（当日の進行役） | 幹事画面（手元の端末） | 開催回ごとの ID / PASS でログインし、問題を送る、回答状況を確認する、順位発表で好きな順位の人を投影する |
| （会場のプロジェクター） | 投影画面（幹事画面とは別のパソコン） | 問題・結果・順位を会場に映す。幹事画面の操作に従って表示が切り替わる |
| 参列者（1 回の式で最大 120 人程度） | 参列者画面 | QR コードからアクセスし、ニックネームを入れて参加し、4 択で解答する |

## 3. ゴール / 非ゴール / アンチゴール

### ゴール
- 1 回の式で 120 人程度が同時に参加しても、問題の切り替えや回答受付が遅延なく全員に反映される（企画書の目安は 100 人。負荷試験は 150 接続で行う）
- 参列者は QR コードを読み取ってニックネームを入れるだけで参加できる（アカウント登録やアプリのインストールは不要）
- 順位発表を幹事が操作し、好きな順位の人を好きな順で投影できる
- 同じ問題セットで、リハーサル回・本番回のように何度でも開催できる

### 非ゴール（今回は作らない）
- 有料化、決済、主催者アカウントのセルフ登録（アカウントはシステム管理者が作る）
- 4 択以外の問題形式（記述式、並べ替えなど）
- 回答の速さによる加点
- 同点者の決着をシステムで付けること（会場でじゃんけんをして決める）

### アンチゴール（機能が揃っていても失敗とみなすもの）
- 本番中にアクセスの集中で画面が固まり、進行が止まる
- 参列者のスマホがスリープや再読み込みで途切れたときに、参加し直せない、または点数が消える

## 4. 機能要件

### 4.1 管理画面（システム管理者・主催者）
- システム管理者は主催者のアカウントを作る。
- システム管理者の「ログ確認」は、Cloudflare（Workers）と Cloud Run のログをそれぞれのコンソールで見ることを指す。アプリにログ閲覧の画面は作らない。
- 主催者 1 人が持つ問題セットは 1 つ。まず動くものを作るため、複数の問題セットには対応しない。
- 主催者は管理画面にログインして使う。画面は次のとおり（`UI作成.md`、スケッチ b4）。
  - **トップページ**: 質問解答の数、質問解答一覧への遷移、開催回のタイトル一覧、開催回作成への遷移
  - **質問解答一覧**: 質問と解答の一覧、新規作成。クリックで編集へ
  - **質問解答の作成・編集**: 質問のタイトル、画像（アップロードしてプレビュー）、選択肢 A〜D、正解の選択、保存
  - **開催回作成**: 開催回名を入力して作成
  - **開催回詳細**: 幹事の ID / PASS、作成した時点の質問解答
- 開催回を作った時点の問題一式をその開催回で使い続ける。あとで問題を直しても、作成済みの開催回には反映しない。反映させたい場合は新しい開催回を作る。

### 4.2 幹事画面と投影画面（当日の進行）
幹事画面と投影画面は別の画面で、それぞれ別のパソコンで開く。幹事画面は進行操作と確認のための画面で、会場には映さない。投影画面は会場のプロジェクターにつないだパソコンで開き、操作はせず、幹事画面の操作に従って表示が切り替わる。

幹事画面の流れは次のとおり（`UI作成.md`、スケッチ b5）。

1. **ログイン**: 開催回詳細に表示された ID / PASS を入力する。ID / PASS は当面の手段で、別の方式に置き換える予定（「8. 未決事項」）。
2. **開始待機**: イベント名と、現在の参加人数（リアルタイムで増える）を表示する。投影画面には参加用の QR コードも表示する。「次へ進む」で第 1 問へ。
3. **問題表示**: 何問目か、問題文、画像（あれば）、選択肢、解答を送信した人数を表示する。「締め切り」で回答の受付を止め、続けて「正解発表」で解答表示へ進む。締め切りと正解発表は別の操作とする（現在の実装の 3 段階 `open` → `closed` → `revealed` をそのまま使う）。早押しではないので、締め切りを厳密にする必要はない。
4. **解答表示**: 何問目か、問題文、選択肢、正解、選択肢ごとの回答人数を表示する。「次の問題へ」で次の問題へ進む。最後の問題のあとは順位一覧へ。
5. **順位一覧**: 全員のニックネームと順位を幹事が確認する。選んだ人の順位表示へ進む。
6. **順位表示**: 選んだ人の順位と名前を、「順位を投影」「名前を投影」のボタンで別々に投影する。「戻る」で順位一覧へ戻り、次の人を選ぶ。

どの順位を、どの順番で発表するかは式によって異なる（上位だけ、特別賞の順位も、など）。そのため、発表の順番をシステムで決めず、幹事が好きな人を好きな順に投影できる作りにする。

### 4.3 参列者画面
画面の流れは次のとおり（`UI作成.md`、スケッチ b6）。

1. **登録**: ニックネームを入力して決定する。同じ開催回の中で同じニックネームは使えない。
2. **待機**: 問題が出るまで「待機中」と表示する。あわせて、これまでの問題ごとに自分が選んだ選択肢と正解・不正解を一覧で表示する（例: 問 1 B ○、問 2 C ×）。正誤は、その問題の正解発表のあとに表示する。自分の順位は最後まで表示しない。
3. **回答**: 問題文、画像、選択肢を表示する。選択肢を選んで決定する。締め切りまでは選び直せる。締め切られたら待機に戻る。

スタート後も参加できる（途中参加）。参加前の問題は 0 点のまま。順位発表が始まったら参加を締め切る。

### 4.4 採点と順位
- 正解した問題の数を点数とする（問題ごとの配点は設けない）。回答の速さは関係ない。
- 出題順は、問題を作成した順とする（並べ替えの機能は作らない）。
- 同点の人は同じ順位にする（例: 90 点が 2 人なら 2 人とも 1 位で、次の人は 3 位）。決着は会場のじゃんけんで付け、その結果はシステムに入力しない。

### 4.5 途切れたときの復帰
- 参列者の端末には参加 ID を保存しておく。スリープや再読み込みのあとに参列者画面を開き直したら、同じニックネームと点数のまま、いまの進行状況に自動で戻る。
- 幹事画面・投影画面が再読み込みやフリーズをしても、開き直せば進行中の状態から再開できる。進行状況はサーバー側で持ち、ブラウザ側では持たない。
- 別のブラウザで開き直した場合（LINE のアプリ内ブラウザから Safari に移るなど）は復帰させない。新しい参加者として 0 点から参加し直してもらう。

### 4.6 リハーサルと開催回
- 1 つの問題セットについて、開催回を何度でも作れる。リハーサルで 1 回、本番で 1 回、のように使う。
- 開催回ごとに参加者・回答・点数はまっさらになる。参列者用の QR コード（URL）も開催回ごとに変わる。
- 各開催回の結果は Cloudflare 側（`apps/live`）だけが持ち、Rails には取り込まない・保存しない。管理画面では順位や結果の状況を見ない（2026-11-07 の決定）。

## 5. 構成

スケッチ b2 のとおり、役割を 2 つに分ける。

- **Rails（GCP）**: 事前準備と記録を担う。
- **Cloudflare（Worker + Durable Object + R2）**: 当日の進行をすべて受け持つ。

当日は参列者からのアクセスが Rails に届かない構成にして、アクセス集中の影響を Cloudflare 側だけで受け止める。

```
[システム管理者 / 主催者] ──▶ Rails（GCP） ──(開催回作成時に問題一式を送る)──▶ Durable Object（開催回ごとに 1 つ）
                               ▲                                                ▲         ▲         ▲
                                                                          WebSocket │         │         │
                                                                         [幹事画面] [投影画面] [参列者のスマホ ×120]
画像: Rails からアップロード ──▶ R2 ──(CDN)──▶ 投影画面・参列者画面
```

データの関係はスケッチ b3 のとおり、主催者 ― 問題セット ― 開催回 ― 参列者。幹事は開催回に結びつく。

| 部品 | 役割 |
|---|---|
| Rails 8（`apps/admin`） | システム管理者・主催者のログイン、主催者アカウントの作成、問題の CRUD、画像アップロード、開催回の作成と幹事 ID / PASS の発行、問題一式と幹事 ID / パスワードのハッシュを Durable Object へ送ること。結果の取り込み・保存はしない |
| Cloudflare Workers（`apps/live`） | 幹事画面・投影画面・参列者画面の配信、WebSocket の受け口 |
| Durable Object | 開催回ごとに 1 インスタンス。進行状態、参加者、回答、点数を持ち、WebSocket で全員に一斉配信する |
| R2 | 問題画像の保存と CDN 配信 |

### 5.1 技術選定
| 項目 | 選定 |
|---|---|
| 管理画面 | Rails 8 |
| 管理画面の DB | PostgreSQL（Neon の無料枠）。Cloud Run はディスクが永続化されず、インスタンスが複数立つこともあるため、SQLite は使わない |
| 管理画面のログイン | Rails 8 標準の認証ジェネレーター。ユーザーはシステム管理者と主催者 |
| 管理画面のホスティング | Google Cloud Run |
| 幹事画面・投影画面・参列者画面 | React + Vite（TypeScript）。Workers の静的アセットとして配信 |
| Workers の API | Hono |
| リアルタイム通信 | Durable Object + WebSocket |
| 画像 | R2（Rails の Active Storage から S3 互換 API でアップロード） |
| リポジトリ構成 | モノレポ。`apps/admin`（Rails）、`apps/live`（Cloudflare）。JavaScript 側は pnpm workspace で管理する |

## 6. 制約
- 企画書の期限 11/8 は、最低限動くもの（MVP）を用意する期限。最初の本番は 2026 年 12 月。範囲を広げない。
- 1 回の式の参加者は最大 120 人程度。
- 本番の会場のネットワーク環境は式場によって異なる。

## 7. 実装者に任せること
- 幹事の操作ミスを取り消す機能（1 つ前の段階に戻るなど）の要否
- 画面のデザインや演出の細部（色、フォント、アニメーションなど）
- Rails と Durable Object 間の認証方式、API の形
- テストの方針

## 8. 未決事項

`docs/requirements/` から読み取れない、または旧設計・現在の実装と食い違っている点。決まったらこの節から本文へ移す。

1. **幹事のログイン方式（最終形）**: 当面は開催回ごとの ID / PASS とし、のちに別の方式を考える。現在の実装は URL に入れたホストトークン（HMAC）。

### 決定済み（2026-11-07）

- 期限 11/8 は MVP の期限（→ 6. 制約）。
- 幹事画面と投影画面は別の画面で、別のパソコンで開く（→ 4.2）。現在の `apps/live` は `/host/:id` が両方を兼ねているので、分ける必要がある。
- 順位発表は、幹事が好きな人を好きな順に投影する（→ 4.2）。現在の `apps/live` の「4 位〜XX 位の一覧 → 3 位・2 位・1 位を順にめくる」流れは作り直しになる。
- 参列者画面には各問の自分の回答と正誤を一覧で見せる。順位は見せない（→ 4.3）。
- 締め切りと正解発表は別の操作のままにする（→ 4.2）。現在の `apps/live` の `q:<i>:open|closed|revealed` の 3 段階と `PhaseKey` のエンコーディングは変えない。
- 問題の項目はタイトル・画像・選択肢 A〜D・正解のみ。説明（幹事用メモ）・配点・並べ替え・上位一覧の表示人数（XX）は作らない。点数は正解数（→ 4.1、4.4）。
- システム管理者のログ確認は Cloudflare と Cloud Run のコンソールで行う。アプリの機能にはしない（→ 4.1）。
- 主催者 1 人につき問題セットは 1 つ（→ 4.1）。
- 結果の取り込み・保存は作らない。管理画面では順位や結果の状況を見ない（→ 4.6、5）。`apps/live` の `GET /api/sessions/:id/ranking` は残るが、admin は呼ばない。この決定で、旧設計の「最終結果を Rails に保存する」と資料・実装の食い違いが一つ解消した。
