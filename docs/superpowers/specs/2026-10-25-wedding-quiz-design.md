# Makunouchi 要件定義・設計

作成日: 2026-10-25

## 1. 目的と背景

結婚式の披露宴の余興として、ゲストが自分のスマホから参加する 4 択クイズを実施するためのシステム。

- オーナー（本リポジトリの作者）が幹事として、**友人の結婚式 5 回**で使う。最初の本番は **2026 年 12 月**。
- 有料化や一般公開は考えていない。ただし、知り合いの範囲で使えるようにインターネット上には公開する。
- 将来、オーナー以外の人が幹事として使える余地は残すが、今回は作らない。

**最も重要な品質**: 披露宴の最中に、アクセスの集中で画面が固まって進行が止まることが絶対に起きないこと。構成上の判断はすべてこれを最優先にする。

## 2. 利用者

| 利用者 | 端末 | やること |
|---|---|---|
| 幹事（オーナー） | PC（画面をプロジェクターで会場に投影） | 当日の進行操作。進行画面がそのまま投影画面になる |
| 幹事（オーナー） | スマホ | 管理画面にログインし、全員の順位を手元で確認する（特別賞の確認用） |
| 幹事（オーナー） | PC（事前） | 式ごとのクイズを作成・編集する |
| ゲスト（1 回の式で 30〜120 人） | 自分のスマホ | 会場の QR コードを読み取って参加し、4 択で回答する |

## 3. ゴール / 非ゴール / アンチゴール

### ゴール
- 1 回の式で 120 人が同時に参加しても、問題の切り替えや回答受付が遅延なく全員に反映される
- ゲストは QR コードを読み取ってニックネームを入れるだけで参加できる（アカウント登録やアプリのインストールは不要）
- 1 位〜3 位をめくる演出で、会場を盛り上げられる
- 管理画面で式ごとにクイズを作り分け、5 回の式で使い回せる

### 非ゴール（今回は作らない）
- 有料化、決済、一般ユーザーの新規登録
- オーナー以外の幹事アカウント（複数ユーザー対応）
- 4 択以外の問題形式（記述式、並べ替えなど）
- 回答の速さによる加点
- 同点者の決着をシステムで付けること（会場でじゃんけんをして決める）

### アンチゴール（機能が揃っていても失敗とみなすもの）
- 本番中にアクセスの集中で画面が固まり、進行が止まる
- ゲストのスマホがスリープや再読み込みで途切れたときに、参加し直せない、または点数が消える

## 4. 当日の流れ（機能要件）

### 4.1 受付
- 投影画面に、式のタイトル、参加用の QR コード、参加人数（リアルタイムで増える）を表示する。
- ゲストは QR コードからゲスト画面を開き、ニックネームを入力して参加する。
- 同じ開催回の中で同じニックネームは使えない（入力時に「その名前は使われています」と返す）。めくる演出や特別賞の確認で、誰のことか分からなくなるのを防ぐため。（作者の判断）
- 幹事が「スタート」を押すと第 1 問に進む。
- スタート後も参加できる（途中参加）。参加前の問題は 0 点のまま。最終結果の発表が始まったら参加を締め切る。（作者の判断）

### 4.2 出題と回答（各問題で繰り返す）
1. 幹事が出題する。投影画面とゲスト画面の両方に、問題が自動で一斉に表示される。
   - 投影画面には、第 N 問 / 全 M 問、タイトル、画像（あれば）、選択肢 A〜D、回答済み人数を表示する。
   - ゲスト画面には、タイトルと選択肢 A〜D のボタンを表示する。
   - 問題の説明は幹事が口頭で読み上げるため、画面に表示する必要はない。
2. ゲストは 4 択から 1 つを選んで回答する。締め切るまでは選び直せる。
3. 幹事が「回答を締め切る」を押す。これ以降は回答を受け付けない。
4. 幹事が正解を発表する。
   - 投影画面には、正解と、選択肢ごとの回答人数（棒グラフ）を表示する。
   - ゲスト画面には、正解・不正解と、自分の現在の点数を表示する。
5. 幹事が「次の問題へ」を押す。最後の問題が終わったら、最終結果の発表に進む。

### 4.3 最終結果の発表
発表の順序は次のとおり。

1. 投影画面に **4 位〜XX 位** の一覧（ニックネームと点数）を表示する。XX は式ごとに幹事が設定する。
2. 3 位の欄を伏せた状態で表示し、幹事の操作でめくって名前と点数を見せる。
3. 2 位、1 位も同じ手順で 1 人ずつめくる。

各画面の扱いは次のとおり。

- **ゲスト画面**: 自分の順位と点数を表示する。1 位〜3 位のネタバレを防ぐため、表示するのは 1 位をめくり終えた後とし、それまでは「結果発表中」と表示する。（作者の判断）
- **幹事のスマホ（管理画面）**: 全員の順位を表示する。最下位から二番目賞や 50 位賞などの特別賞の確認に使う。進行中も含めていつでも見られ、その時点の順位を Durable Object から取得して表示する。（作者の判断）

### 4.4 採点と順位
- 正解した問題の配点を合計したものを点数とする。回答の速さは関係ない。
- 配点は、クイズ全体の初期値（例: 10 点）を各問題に入れ、問題ごとに変更できる。
- 同点の人は同じ順位にする（例: 90 点が 2 人なら 2 人とも 1 位で、次の人は 3 位）。めくる演出では、同じ順位の全員の名前をまとめて表示する。決着は会場のじゃんけんで付け、その結果はシステムに入力しない。

### 4.5 途切れたときの復帰
- ゲストの端末には参加 ID を保存しておく。スリープや再読み込みのあとにゲスト画面を開き直したら、同じニックネームと点数のまま、いまの進行状況に自動で戻る。
- 幹事の PC が再読み込みやフリーズをしても、開き直せば進行中の状態から再開できる。進行状況はサーバー側で持ち、ブラウザ側では持たない。
- 別のブラウザで開き直した場合（LINE のアプリ内ブラウザから Safari に移るなど）は**復帰させない**。新しい参加者として 0 点から参加し直してもらう。なりすましを防ぐため、ニックネームを入れ直しても以前の参加者としては扱わない。以前のニックネームは使用済みのままなので、別の名前で参加することになる。

### 4.6 リハーサルと開催回
- 1 つの式（クイズ）について、「開催回」を何度でも新しく始められる。本番前のリハーサルで 1 回、本番で 1 回、のように使う。
- 開催回ごとに参加者・回答・点数はまっさらになる。ゲスト用の QR コード（URL）も開催回ごとに変わる。前の開催回の QR を読んだゲストが本番に混ざらないようにするため。（URL を変えるのは作者の判断）
- 開催回を始めた時点の問題一式を Durable Object に送り、その開催回の間はそれを使い続ける。開催回の途中で管理画面から問題を直しても、進行中のクイズには反映しない（意図した仕様）。直した内容を反映させたい場合は、新しい開催回を始める。
- 各開催回の最終結果は Rails に保存する。リハーサルか本番かを区別できるようにする。

### 4.7 事前準備（管理画面）
- 幹事はログインして、式（イベント）を作成する。式ごとに、タイトル、上位一覧の表示人数（XX）、配点の初期値を設定する。
- 式ごとに 5〜15 問を作成する。各問題に設定する項目は、タイトル、説明（任意で、幹事用のメモとして使う）、画像（任意）、選択肢 4 つ、正解 1 つ、配点。
- 問題は並べ替えられる。

## 5. 構成

役割を 2 つに分ける。

- **Rails**: 事前準備と記録を担う。
- **Cloudflare**: 当日の進行をすべて受け持つ。

当日はゲストからのアクセスが Rails に届かない構成にして、アクセス集中の影響を Cloudflare 側だけで受け止める。

```
[幹事 PC / 管理画面] ──(事前準備)──▶ Rails ──(開始時に問題一式を送る)──▶ Durable Object（開催回ごとに 1 つ）
                                       ▲                                     ▲        ▲
                         (終了時に結果を保存)                     WebSocket │        │ WebSocket
                                                                [幹事 PC 投影画面]  [ゲストのスマホ ×120]
画像: Rails からアップロード ──▶ R2 ──(CDN)──▶ 投影画面・ゲスト画面
```

| 部品 | 役割 |
|---|---|
| Rails 8（`apps/admin`） | 幹事ログイン、式・問題の CRUD、画像アップロード、当日開始時に問題一式を Durable Object へ送ること、全員の順位表示（幹事のスマホ向け）、最終結果の保存 |
| Cloudflare Workers（`apps/live`） | ゲスト画面と投影画面（進行操作を含む）の配信、WebSocket の受け口 |
| Durable Object | **開催回ごと**に 1 インスタンス。進行状態（いま何問目か、どの段階か）、参加者、回答、点数を持ち、WebSocket で全員に一斉配信する |
| R2 | 問題画像の保存と CDN 配信 |

### 5.1 技術選定（オーナーから任されたもので、作者が判断した）
| 項目 | 選定 |
|---|---|
| 管理画面 | Rails 8 |
| 管理画面の DB | PostgreSQL（Neon の無料枠）。Cloud Run はディスクが永続化されず、インスタンスが複数立つこともあるため、SQLite は使わない。オーナーと合意済み |
| 管理画面のログイン | Rails 8 標準の認証ジェネレーター。ユーザーはオーナー 1 人 |
| 管理画面のホスティング | Google Cloud Run（オーナーの指定） |
| ゲスト画面・投影画面 | React + Vite（TypeScript）。Workers の静的アセットとして配信 |
| Workers の API | Hono |
| リアルタイム通信 | Durable Object + WebSocket |
| 画像 | R2（Rails の Active Storage から S3 互換 API でアップロード） |
| リポジトリ構成 | モノレポ。`apps/admin`（Rails）、`apps/live`（Cloudflare）。JavaScript 側は pnpm workspace で管理する |

## 6. 制約
- 最初の本番は 2026 年 12 月。間に合わせることを最優先にし、範囲を広げない。
- 1 回の式の参加者は最大 120 人程度、問題は 5〜15 問。
- 本番の会場のネットワーク環境は式場によって異なる。

## 7. 実装者に任せること
- 幹事の操作ミスを取り消す機能（1 つ前の段階に戻るなど）の要否
- 同点の人がめくり枠の境界（3 位と 4 位など）をまたぐときの表示
- 画面のデザインや演出の細部（めくるアニメーション、色、フォントなど）
- Rails と Durable Object 間の認証方式、API の形
- 投影画面の進行操作 UI の配置
- テストの方針
