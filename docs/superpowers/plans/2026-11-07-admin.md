# 管理画面（apps/admin、Rails）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** システム管理者と主催者が問題・開催回を準備し、当日進行は `apps/live` に任せ、終了後に順位結果を Rails に保存できる `apps/admin` を作る。

**Architecture:** Rails 8 が事前準備と記録だけを持つ。開催回作成時に問題一式を `PUT /api/sessions/:id` で Cloudflare Workers に送り、結果は `GET /api/sessions/:id/ranking` の `final: true` を見て保存する。当日の WebSocket・採点・投影は `apps/live` 側に寄せ、Rails には参列者のアクセスを届かせない。

**Tech Stack:** Rails 8.1、Ruby 4.0、PostgreSQL（Neon 無料枠）、Cloud Run、Active Storage（R2 の S3 互換 API）、Rails 標準認証（`has_secure_password` + `bcrypt`）、minitest、importmap / turbo / stimulus（雛形のまま）

**Spec:** `docs/superpowers/specs/2026-10-25-wedding-quiz-design.md`（4.1、4.4、4.6、5、8 章「決定済み」）、`docs/requirements/`（企画書・行動シナリオ・UI作成・スケッチ b3/b4）。`apps/live` 側の最新契約は `makunouchi-plans-1107` の `2026-11-07-*.md`（特に `remove-points-and-topn` と `split-host-and-screen`、`free-order-results` の `final` 決定）を正とする。

## Global Constraints

- 要件の正は `docs/requirements/`。設計書と食い違うときは要件を優先する。
- 管理画面は Cloud Run、DB は Neon の PostgreSQL。SQLite は本番に使わない（Cloud Run のディスクは永続化されず、インスタンスも複数になりうる）。
- 主催者アカウントのセルフ登録は作らない。システム管理者が作る。
- 主催者 1 人につき問題セットは 1 つ。複数セットは作らない。
- 問題は 4 択のみ。項目はタイトル・画像・選択肢 A〜D・正解。配点・説明（幹事メモ）・並べ替え・上位一覧人数（topN）は作らない。出題順は作成順（`id` または `created_at` 昇順）。
- 問題数は live 側の制約どおり 5〜15 問。開催回作成時に足りなければ作らせない。
- 開催回を作った時点の問題一式をスナップショットとして使う。あとで問題を直しても作成済み開催回には反映しない。
- 開催回 ID は Rails が発行する UUID（`SecureRandom.uuid`）。live 側の形式は `/^[A-Za-z0-9_-]{1,100}$/`（`:` 不可）。不一致時 live は（split-host 後）`400 { "error": "invalid_session_id" }`。
- `ADMIN_API_SECRET` は Rails と Workers で同じ値（32 文字以上）。API は `Authorization: Bearer <ADMIN_API_SECRET>`。
- 幹事トークン: `HMAC-SHA256(ADMIN_API_SECRET, sessionId)` の hex。投影画面トークン: `HMAC-SHA256(ADMIN_API_SECRET, "screen:" + sessionId)` の hex。
- ペイロードに `points` と `topN` を入れない（live の `2026-11-07-remove-points-and-topn`）。
- ranking の `final` の**目標意味**は「結果発表に入った時点（`phase.type === "results"`）で `true`」（`2026-11-07-free-order-results` 確認事項 4 → A）。**Task 6 の結合は free-order-results のマージ後に限定する**（下記「live 結合の待ち方」）。現行 worktree の `isFinal`（1 位 podium めくり後など）とは意味が違うので、free-order 前の live に対して Task 6 を結合して通す想定は書かない。
- システム管理者のログ確認画面は作らない（Cloudflare / Cloud Run のコンソールで見る）。
- 範囲を広げない（MVP）。決済・有料化・幹事ログインの最終形・複数問題セットは扱わない。
- テストは Rails 標準の minitest（モデル・リクエスト）。system test は認証→問題→開催回作成（live は stub）の Happy Path を Task 5 末尾で 1 本。
- UI 文言は日本語。ビュー直書き、または `config/locales/ja.yml` を足す（`en.yml` のみのままにしない）。
- `filter_parameter_logging` に `password` / `host_password` / `ADMIN_API_SECRET` 相当を足し、ログに出さない。

## Review Focus

1. **master.key / 秘密の漏えい**: `config/master.key`、`ADMIN_API_SECRET`、R2 の鍵がリポジトリや Cloud Run のログに出ないこと。→ Task 1 の gitignore 確認と Task 2/4/7 の `filter_parameter_logging`。
2. **ペイロードの形ずれ**: `points` / `topN` を送る、選択肢が 4 つでない、`imageUrl` が http、問題数が 5 未満だと live が 422 にする。→ Task 5（本番画像は https の R2 URL。→ Active Storage 切替）。
3. **開催回の DB と live PUT の補償**: live は同一 ID の再 PUT が常に 409（削除 API なし）。pending → PUT → ready と同一 `public_id` 再試行を守らないと孤児 DO や誤解の 409 になる。→ Task 5。
4. **未確定の ranking を保存する**: `final: false` の応答を結果として保存してはいけない。→ Task 6（free-order マージ後の `final` 意味で結合）。
5. **主催者が他人の問題・開催回を触る**: 認可で主催者は自分のデータだけ。システム管理者は主催者作成だけ（MVP では主催者作成に限定してよい）。→ Task 2・3。

### live 結合の待ち方（前提: 確認事項 7 の A）

| admin 作業 | 待つ live の段 |
|---|---|
| Task 5（ペイロード PUT・結合） | **points / topN 削除**（`remove-points-and-topn`）のマージ後 |

| Task 6（ranking 保存・結合） | **free-order-results** のマージ後 |

補足: 順位を好きな順に投影する実装（`free-order-results`）は方針が変わり、スタックの段 5 として先に入る予定（別ワーカーが実装中）。**Task 6 は free-order-results のマージ後に結合する。** それまではモデル／ジョブの骨組みや stub テストまでは進めてよいが、本番相当の live への結合テストは free-order 後とする。

### 認証・トークン

| 用途 | 計算 |
|---|---|
| API | リクエストヘッダ `Authorization: Bearer <ADMIN_API_SECRET>` |
| 幹事（host） | `OpenSSL::HMAC.hexdigest("SHA256", ADMIN_API_SECRET, session_id)` |
| 投影画面（screen） | `OpenSSL::HMAC.hexdigest("SHA256", ADMIN_API_SECRET, "screen:#{session_id}")` |

参照: `apps/live/src/worker/auth.ts` の `hostTokenFor` /（予定）`screenTokenFor`、`index.ts` の Bearer 検証。

### 開催回の登録

`PUT {LIVE_BASE_URL}/api/sessions/:sessionId`

```json
{
  "title": "開催回のタイトル（1〜100 文字）",
  "questions": [
    {
      "title": "問題文（1〜200 文字）",
      "imageUrl": "https://... または null",
      "choices": ["A", "B", "C", "D"],
      "correctIndex": 0
    }
  ]
}
```

- `questions` は 5〜15 件。各 `choices` は 1〜50 文字 × ちょうど 4。`correctIndex` は 0〜3。
- **`points` と `topN` は送らない。**
- 応答:
  - 成功: `201 { "ok": true }`
  - 既にある: `409 { "error": "exists" }`
  - ペイロード不正: `422 { "error": "invalid_payload", "issues": [...] }`
  - 開催回 ID 形式不正（split-host 後）: `400 { "error": "invalid_session_id" }`
  - 未認証: `401`
  - シークレット不足: `500 { "error": "misconfigured" }`
- 参照: `apps/live/src/worker/payload.ts`、`index.ts` の `PUT`、split-host 計画の `isValidSessionId`。

### 結果の取得

`GET {LIVE_BASE_URL}/api/sessions/:sessionId/ranking`

```json
{
  "phaseKey": "r:list",
  "final": true,
  "players": [
    { "playerId": "…", "nickname": "…", "score": 3, "rank": 1 }
  ]
}
```

- `final` が `true` のときだけ Rails は結果を確定保存する（`players` をそのまま永続化）。
- **目標契約**（free-order-results 後）: `final === (phase.type === "results")`。全問採点が確定した時点。
- **現行コード**（free-order 前）: `isFinal` は結果フェーズかつ「1 位の podium をめくった後」等。Task 6 はこの意味には結合しない。
- 開催回未作成: `404 { "error": "not_found" }`。
- 参照: `session-room.ts` の `ranking()`、`ranking.ts` の `RankedPlayer` /（現行）`isFinal`、free-order 計画 Task 3。

### URL（開催回詳細に出す）

- 参列者: `{LIVE_PUBLIC_URL}/s/{sessionId}`
- 幹事: `{LIVE_PUBLIC_URL}/host/{sessionId}?token={hostToken}`
- 投影: `{LIVE_PUBLIC_URL}/screen/{sessionId}?token={screenToken}`（**split-host-and-screen マージ後**に出す。それまでは幹事 URL と参列者 URL のみでも可）

## 雛形の整理（判断）

取り込み済みの Rails new 雛形（sqlite3・Kamal・solid_cache / solid_queue・importmap）を次のように直す。

| 項目 | 判断 | 理由 |
|---|---|---|
| DB | `sqlite3` gem を外し `pg` へ。`database.yml` は Neon の URL を読む。cache/queue の database 構成は確認事項 6 | 設計書 5.1。Cloud Run では SQLite 不可 |
| デプロイ | `.kamal/` と `config/deploy.yml`、`kamal` gem、`bin/kamal` を削除。ネストした `apps/admin/.github/**` も削除（モノレポではルート以外の Actions は動かない）。Dockerfile を Cloud Run 向けに直す（`PORT` 尊重、既定 8080、Thruster 可） | ホスティングは Cloud Run |
| solid_cache | **残す**。構成は確認事項 6 | 管理画面のトラフィックは小さく Neon 無料枠で足りる |
| solid_queue | **残す**。Puma プラグイン想定。scale-to-zero 制約は確認事項 5 | 別ワーカーサービスを増やさない |
| Neon 接続 | Cloud Run からは **プール接続用 URL**（Neon pooled） | インスタンス数 × スレッドで接続が溢れないようにする |
| Active Storage | 本番は R2（S3 互換）。開発は Disk。`production.rb` の service を R2 に切り替え、公開 URL が **https** になることを確認（live の `imageUrl` 制約） | Disk のままでは開催回作成が 422 |
| pnpm | ルート `pnpm-workspace.yaml` の `apps/*` は、admin に `package.json` が無い限り無視される。誤解防止に Task 1 で「admin は Rails のみ・JS パッケージにしない」と README / コメントに一言 | 任意だが運用ミス防止 |
