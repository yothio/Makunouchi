# 管理画面（apps/admin、Rails）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** システム管理者と主催者が問題・開催回を準備し、当日進行は `apps/live` に任せ、終了後に順位結果を Rails に保存できる `apps/admin` を作る。

**Architecture:** Rails 8 が事前準備と記録だけを持つ。開催回作成時に問題一式を `PUT /api/sessions/:id` で Cloudflare Workers に送り、結果は `GET /api/sessions/:id/ranking` の `final: true` を見て保存する。当日の WebSocket・採点・投影は `apps/live` 側に寄せ、Rails には参列者のアクセスを届かせない。

**Tech Stack:** Rails 8.1、Ruby 4.0、PostgreSQL（Neon 無料枠）、Cloud Run、Active Storage（R2 の S3 互換 API）、Rails 標準認証（`has_secure_password`）、minitest、importmap / turbo / stimulus（雛形のまま）

**Spec:** `docs/superpowers/specs/2026-10-25-wedding-quiz-design.md`（4.1、4.4、4.6、5、8 章「決定済み」）、`docs/requirements/`（企画書・行動シナリオ・UI作成・スケッチ b3/b4）。`apps/live` 側の最新契約は `makunouchi-plans-1107` の `2026-11-07-*.md`（特に `remove-points-and-topn` と `split-host-and-screen`、`free-order-results` の `final` 決定）を正とする。

## Global Constraints

- 要件の正は `docs/requirements/`。設計書と食い違うときは要件を優先する。
- 管理画面は Cloud Run、DB は Neon の PostgreSQL。SQLite は本番に使わない（Cloud Run のディスクは永続化されず、インスタンスも複数になりうる）。
- 主催者アカウントのセルフ登録は作らない。システム管理者が作る。
- 主催者 1 人につき問題セットは 1 つ。複数セットは作らない。
- 問題は 4 択のみ。項目はタイトル・画像・選択肢 A〜D・正解。配点・説明（幹事メモ）・並べ替え・上位一覧人数（topN）は作らない。出題順は作成順（`id` または `created_at` 昇順）。
- 問題数は live 側の制約どおり 5〜15 問。開催回作成時に足りなければ作らせない。
- 開催回を作った時点の問題一式をスナップショットとして使う。あとで問題を直しても作成済み開催回には反映しない。
- 開催回 ID は Rails が発行する UUID（`SecureRandom.uuid`）。live 側の形式は `/^[A-Za-z0-9_-]{1,100}$/`（`:` 不可）。
- `ADMIN_API_SECRET` は Rails と Workers で同じ値（32 文字以上）。API は `Authorization: Bearer <ADMIN_API_SECRET>`。
- 幹事トークン: `HMAC-SHA256(ADMIN_API_SECRET, sessionId)` の hex。投影画面トークン: `HMAC-SHA256(ADMIN_API_SECRET, "screen:" + sessionId)` の hex。
- ペイロードに `points` と `topN` を入れない（live の `2026-11-07-remove-points-and-topn`）。
- ranking の `final` は結果発表に入った時点（`phase.type === "results"`）で `true`（live の `2026-11-07-free-order-results` 確認事項 4 → A）。保存対象は `final: true` のときの `players`。
- システム管理者のログ確認画面は作らない（Cloudflare / Cloud Run のコンソールで見る）。
- 範囲を広げない（MVP）。決済・有料化・幹事ログインの最終形・複数問題セットは扱わない。
- テストは Rails 標準の minitest（モデル・リクエスト）。system test は認証と開催回作成の Happy Path 1 本まで。

## Review Focus

1. **master.key / 秘密の漏えい**: `config/master.key`、`ADMIN_API_SECRET`、R2 の鍵がリポジトリや Cloud Run のログに出ないこと。→ Task 1 の gitignore 確認と Task 7 の環境変数。
2. **ペイロードの形ずれ**: `points` / `topN` を送る、選択肢が 4 つでない、`imageUrl` が http、問題数が 5 未満だと live が 422 にする。→ Task 5。
3. **開催回の二重作成**: 同じ UUID で再 PUT すると live は 409。Rails 側も開催回レコードを二重に作らない。→ Task 5。
4. **未確定の ranking を保存する**: `final: false` の応答を結果として保存してはいけない。→ Task 6。
5. **主催者が他人の問題・開催回を触る**: 認可で主催者は自分のデータだけ。システム管理者は主催者作成だけ（他人の問題編集は任意でもよいが、MVP では主催者作成に限定してよい）。→ Task 2・3。

## apps/live との約束事（送受信の正確な形）

実装時点のこの worktree の `apps/live` はまだ `points` / `topN` を必須にしている。**本計画が前提にする契約は、plans worktree の 2026-11-07 決定後の形**とする。live 側の該当 PR がマージされるまで、結合確認はそちらを待つか、ローカルで同変更を入れた live に対して行う。

### 認証・トークン

| 用途 | 計算 |
|---|---|
| API | リクエストヘッダ `Authorization: Bearer <ADMIN_API_SECRET>` |
| 幹事（host） | `OpenSSL::HMAC.hexdigest("SHA256", ADMIN_API_SECRET, session_id)` |
| 投影画面（screen） | `OpenSSL::HMAC.hexdigest("SHA256", ADMIN_API_SECRET, "screen:#{session_id}")` |

参照: `apps/live/src/worker/auth.ts` の `hostTokenFor` /（予定）`screenTokenFor`、`index.ts` の Bearer 検証。

### 開催回の登録

`PUT {LIVE_BASE_URL}/api/sessions/:sessionId`

```json
{
  "title": "開催回のタイトル（1〜100 文字）",
  "questions": [
    {
      "title": "問題文（1〜200 文字）",
      "imageUrl": "https://... または null",
      "choices": ["A", "B", "C", "D"],
      "correctIndex": 0
    }
  ]
}
```

- `questions` は 5〜15 件。各 `choices` は 1〜50 文字 × ちょうど 4。`correctIndex` は 0〜3。
- **`points` と `topN` は送らない。**
- 成功: `201 { "ok": true }`。既にある: `409 { "error": "exists" }`。不正: `422 { "error": "invalid_payload", "issues": [...] }`。未認証: `401`。シークレット不足: `500 { "error": "misconfigured" }`。
- 参照: `apps/live/src/worker/payload.ts`、`index.ts` の `PUT`。

### 結果の取得

`GET {LIVE_BASE_URL}/api/sessions/:sessionId/ranking`

```json
{
  "phaseKey": "r:list",
  "final": true,
  "players": [
    { "playerId": "…", "nickname": "…", "score": 3, "rank": 1 }
  ]
}
```

- `final` が `true` のときだけ Rails は結果を確定保存する（`players` をそのまま永続化）。
- 開催回未作成: `404 { "error": "not_found" }`。
- 参照: `session-room.ts` の `ranking()`、`ranking.ts` の `RankedPlayer`。`final` の意味は free-order-results 計画で「`results` に入ったら true」に変わる。

### URL（開催回詳細に出す）

- 参列者: `{LIVE_PUBLIC_URL}/s/{sessionId}`
- 幹事: `{LIVE_PUBLIC_URL}/host/{sessionId}?token={hostToken}`
- 投影: `{LIVE_PUBLIC_URL}/screen/{sessionId}?token={screenToken}`（live の split-host-and-screen 後）

## 雛形の整理（判断）

取り込み済みの Rails new 雛形（sqlite3・Kamal・solid_cache / solid_queue・importmap）を次のように直す。

| 項目 | 判断 | 理由 |
|---|---|---|
| DB | `sqlite3` gem を外し `pg` へ。`database.yml` は `DATABASE_URL`（Neon）を読む | 設計書 5.1。Cloud Run では SQLite 不可 |
| デプロイ | `.kamal/` と `config/deploy.yml`、`kamal` gem、`bin/kamal` を削除。Dockerfile を Cloud Run 向けに直す（PORT 環境変数、`EXPOSE 8080`、Thruster は残してよい） | ホスティングは Cloud Run |
| solid_cache | **残す**。本番は Neon 上の cache DB（または同一 DB の cache schema） | 管理画面のトラフィックは小さく、Neon 無料枠で足りる。Cloud Run のメモリキャッシュだけだとインスタンス間で共有できない |
| solid_queue | **残す**。結果取得ジョブ用。Puma の solid_queue プラグインで同一 Cloud Run サービス内実行 | 別ワーカーサービスを増やすと運用が増える。ジョブがほぼ無いのでインプロセスで十分 |
| Neon 接続 | Cloud Run からは **プール接続用 URL**（Neon pooled）を使う | インスタンス数 × スレッドで接続が溢れないようにする |
| Active Storage | 本番は R2（S3 互換）。開発は Disk | 設計書の画像経路 |

## ユーザーに確認すること

1. **幹事ログインの当面の出し方**
   - **A（推奨）**: 開催回詳細に幹事 URL（host トークン付き）と投影 URL（screen トークン付き）を出し、ID/PASS 欄は「将来用の表示」としてランダムな ID/PASS も併記する。live のログイン画面はまだトークン URL のまま。
   - B: admin にだけ ID/PASS を出し、live 側に ID/PASS → トークン交換 API を追加する（live の追加作業が必要。範囲が広がる）。
   - C: ID/PASS を sessionId + hostToken そのものとして扱う（ID=UUID、PASS=hostToken）。実装は単純だが PASS が長く、投影トークンと混同しやすい。

2. **画像の置き場所**
