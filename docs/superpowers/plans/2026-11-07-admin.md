# 管理画面（apps/admin、Rails）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** システム管理者と主催者が問題・開催回を準備し、当日進行は `apps/live` に任せられる `apps/admin` を作る。あわせて、幹事が ID/パスワードで進行画面に入れるよう `apps/live` に小さな変更を入れる。

**Architecture:** Rails 8 は事前準備だけを持つ。開催回は管理画面で作って Neon に保存し、作成後にその情報（問題一式と幹事の ID・パスワードのハッシュ）を `PUT /api/sessions/:id` で Cloudflare Workers に送る。当日の進行で使う情報は Worker 側から読む。**管理画面では順位や結果の状況を見ない**（取り込み・保存も作らない）。当日の WebSocket・採点・投影・幹事認証は `apps/live` 側に寄せ、Rails には参列者のアクセスを届かせない。画像は管理画面が presigned URL を発行し、ブラウザから R2 に直接アップロードする。

**Tech Stack:** Rails 8.1、Ruby 4.0、PostgreSQL（Neon 無料枠・primary の 1 つだけ）、Cloud Run、Active Storage（R2 の S3 互換 API・direct upload）、Rails 標準認証（`has_secure_password` + `bcrypt`）、Active Job は `:async`、キャッシュはメモリ、minitest、importmap / turbo / stimulus（雛形のまま）

**Spec:** `docs/superpowers/specs/2026-10-25-wedding-quiz-design.md`（4.1、4.4、4.6、5、8 章「決定済み」）、`docs/requirements/`（企画書・行動シナリオ・UI作成・スケッチ b3/b4）。`apps/live` 側の最新契約は `makunouchi-plans-1107` の `2026-11-07-*.md`（特に `remove-points-and-topn` と `split-host-and-screen`）を正とする。

## ユーザー決定（2026-11-07）

以前の「ユーザーに確認すること」は次の決定で置き換えた。各 Task はこれに合わせてある。

0. **全体方針**: 開催回は管理画面で作って Neon に保存し、作成後にその情報を Cloudflare（apps/live）に送る。当日の進行で使う情報は Worker 側から読む。管理画面では順位や結果の状況を見ない（必要ない）。
1. **幹事の ID とパスワード**: 開催回を作成したときに管理画面が作り、開催回の情報と一緒に Worker に送る。Worker 側はそれで簡易な認証をする。幹事への伝え方は口頭。→ live 側の変更が要るので **Task 6（apps/live の変更）** に切り出した。
2. **画像**: R2 に置く。管理画面が presigned URL を発行し、ブラウザから R2 に直接アップロードする。Worker から見える公開 URL をペイロードの `imageUrl` にする。
3. **システム管理者**: `bin/rails db:seed` で環境変数から作る。
4. **結果の取り込み・保存**: 作らない。ranking 保存（旧 Task 6）、`session_result` モデル、`fetch_session_result_job` は計画から外した。
5. **solid_queue**: 使わない（gem と設定を外す）。Active Job は `:async`。
6. **データベース**: Neon の primary の 1 つだけ。solid_cache も外し、キャッシュはメモリ。
7. **live との結合**: live 側の各段の PR がマージされてから行う。

## Global Constraints

- 要件の正は `docs/requirements/`。設計書と食い違うときは要件を優先する。
- 管理画面は Cloud Run、DB は Neon の PostgreSQL（primary 1 つだけ）。SQLite は本番に使わない（Cloud Run のディスクは永続化されず、インスタンスも複数になりうる）。cache / queue 用の別 DB は作らない。
- 主催者アカウントのセルフ登録は作らない。システム管理者が作る。最初のシステム管理者は `bin/rails db:seed` が環境変数（`ADMIN_EMAIL` / `ADMIN_PASSWORD`）から作る。
- 主催者 1 人につき問題セットは 1 つ。複数セットは作らない。
- 問題は 4 択のみ。項目はタイトル・画像・選択肢 A〜D・正解。配点・説明（幹事メモ）・並べ替え・上位一覧人数（topN）は作らない。出題順は作成順（`id` または `created_at` 昇順）。
- 問題数は live 側の制約どおり 5〜15 問。開催回作成時に足りなければ作らせない。
- 開催回を作った時点の問題一式をスナップショットとして使う。あとで問題を直しても作成済み開催回には反映しない。
- 開催回 ID は Rails が発行する UUID（`SecureRandom.uuid`）。live 側の形式は `/^[A-Za-z0-9_-]{1,100}$/`（`:` 不可）。不一致時 live は（split-host 後）`400 { "error": "invalid_session_id" }`。
- `ADMIN_API_SECRET` は Rails と Workers で同じ値（32 文字以上）。API は `Authorization: Bearer <ADMIN_API_SECRET>`。
- 幹事は ID/パスワードで入る（Task 6）。Rails は幹事トークン（HMAC）を計算しない・表示しない。投影画面トークン: `HMAC-SHA256(ADMIN_API_SECRET, "screen:" + sessionId)` の hex（そのまま URL に付ける）。
- ペイロードに `points` と `topN` を入れない（live の `2026-11-07-remove-points-and-topn`）。
- **管理画面は ranking を読まない・結果を保存しない。** 開催回詳細・トップに順位や進行状況は出さない。
- Active Job は `:async`、キャッシュは `:memory_store`。`solid_cache` / `solid_queue` の gem・設定・schema は残さない。
- システム管理者のログ確認画面は作らない（Cloudflare / Cloud Run のコンソールで見る）。
- 範囲を広げない（MVP）。決済・有料化・複数問題セットは扱わない。
- テストは Rails 標準の minitest（モデル・リクエスト）。system test は認証→問題→開催回作成（live は stub）の Happy Path を Task 5 末尾で 1 本。
- UI 文言は日本語。ビュー直書き、または `config/locales/ja.yml` を足す（`en.yml` のみのままにしない）。
- `filter_parameter_logging` に `password` / `host_password` / `ADMIN_API_SECRET` 相当を足し、ログに出さない。

## Review Focus

1. **master.key / 秘密の漏えい**: `config/master.key`、`ADMIN_API_SECRET`、R2 の鍵、Active Record Encryption の鍵がリポジトリや Cloud Run のログに出ないこと。→ Task 1 の gitignore 確認と Task 2/4/7 の `filter_parameter_logging`。
2. **ペイロードの形ずれ**: `points` / `topN` を送る、選択肢が 4 つでない、`imageUrl` が http、問題数が 5 未満だと live が 422 にする。→ Task 5（本番画像は https の R2 公開 URL）。
3. **開催回の DB と live PUT の補償**: live は同一 ID の再 PUT が常に 409（削除 API なし）。pending → PUT → ready と同一 `public_id`・同一ハッシュでの再試行を守らないと孤児 DO や誤解の 409 になる。→ Task 5。
4. **幹事パスワードの扱い**: 平文を live に送らない・ログに出さない。live 側でブルートフォースを止められる（失敗回数制限）。→ Task 4（ハッシュ生成）と Task 6（照合・制限）。
5. **主催者が他人の問題・開催回を触る**: 認可で主催者は自分のデータだけ。システム管理者は主催者作成だけ（MVP では主催者作成に限定してよい）。→ Task 2・3。
6. **画像の直接アップロード**: presigned URL の有効期限が短い・Content-Type とサイズを絞る・R2 バケットの CORS が管理画面のオリジンだけに限られる。→ Task 1・3。

### 認証・トークン

| 用途 | 内容 |
|---|---|
| API（Rails → Worker） | リクエストヘッダ `Authorization: Bearer <ADMIN_API_SECRET>` |
| 幹事（人間） | 開催回ごとの ID/パスワード。Rails が作り、パスワードは**ハッシュにして**Worker に送る（Task 4・6） |
| 幹事（WebSocket） | 既存の HMAC トークン `HMAC-SHA256(ADMIN_API_SECRET, sessionId)` は**そのまま残す**。ログイン成功時に Worker がこのトークンを返す（Task 6）。Rails は計算しない |
| 投影画面 | `OpenSSL::HMAC.hexdigest("SHA256", ADMIN_API_SECRET, "screen:#{session_id}")`（そのまま。Rails が URL に付けて表示） |

参照: `apps/live/src/worker/auth.ts` の `hostTokenFor` /（予定）`screenTokenFor`、`index.ts` の Bearer 検証。

### 開催回の登録

`PUT {LIVE_BASE_URL}/api/sessions/:sessionId`

```json
{
  "title": "開催回のタイトル（1〜100 文字）",
  "questions": [
    {
      "title": "問題文（1〜200 文字）",
      "imageUrl": "https://... または null",
      "choices": ["A", "B", "C", "D"],
      "correctIndex": 0
    }
  ],
  "host": {
    "loginId": "幹事のログイン ID",
    "passwordHash": "pbkdf2-sha256$100000$<saltのbase64>$<hashのbase64>"
  }
}
```

- `questions` は 5〜15 件。各 `choices` は 1〜50 文字 × ちょうど 4。`correctIndex` は 0〜3。
- **`points` と `topN` は送らない。**
- `host` は Task 6 で足す項目（live 側の zod では省略可。省略した開催回は従来どおりトークン URL でしか幹事に入れない）。**admin は常に送る。** 平文のパスワードは送らない。
- `imageUrl` は R2 の公開 URL（`{R2_PUBLIC_BASE_URL}/{blob.key}`）。Worker から見える https でなければならない。
- 応答:
  - 成功: `201 { "ok": true }`
  - 既にある: `409 { "error": "exists" }`
  - ペイロード不正: `422 { "error": "invalid_payload", "issues": [...] }`
  - 開催回 ID 形式不正（split-host 後）: `400 { "error": "invalid_session_id" }`
  - 未認証: `401`
  - シークレット不足: `500 { "error": "misconfigured" }`
- 参照: `apps/live/src/worker/payload.ts`、`index.ts` の `PUT`、split-host 計画の `isValidSessionId`。

### 幹事ログイン（Task 6 で live に足す）

`POST {LIVE_BASE_URL}/api/sessions/:sessionId/host-login`（認証ヘッダ不要。ブラウザから呼ぶ）

```json
{ "loginId": "…", "password": "…" }
```

- 成功: `200 { "token": "<幹事 HMAC トークン>" }`。ブラウザはこれを従来どおり sessionStorage に持ち、`/ws/:id/host?token=` に使う。
- 失敗: `401 { "error": "invalid_credentials" }`（ID 違いとパスワード違いを区別しない）。
- ロック中: `429 { "error": "too_many_attempts" }`。
- 開催回が無い / `host` が登録されていない: `404`。

### URL（開催回詳細に出す）

- 参列者: `{LIVE_PUBLIC_URL}/s/{sessionId}`
- 幹事: `{LIVE_PUBLIC_URL}/host/{sessionId}`（トークンは付けない。ID/パスワードを別欄に表示し、幹事へは口頭で伝える）
- 投影: `{LIVE_PUBLIC_URL}/screen/{sessionId}?token={screenToken}`（**split-host-and-screen マージ後**に出す）

## 雛形の整理（判断）

取り込み済みの Rails new 雛形（sqlite3・Kamal・solid_cache / solid_queue・importmap）を次のように直す。

| 項目 | 判断 | 理由 |
|---|---|---|
| DB | `sqlite3` gem を外し `pg` へ。`database.yml` は Neon の URL を読む **primary 1 つだけ** | 設計書 5.1。Cloud Run では SQLite 不可。cache / queue の別 DB は使わない（決定 6） |
| デプロイ | `.kamal/` と `config/deploy.yml`、`kamal` gem、`bin/kamal` を削除。ネストした `apps/admin/.github/**` も削除（モノレポではルート以外の Actions は動かない）。Dockerfile を Cloud Run 向けに直す（`PORT` 尊重、既定 8080、Thruster 可） | ホスティングは Cloud Run |
| solid_cache | **外す**。gem、`config/cache.yml`、`db/cache_schema.rb` を削除し、`config.cache_store = :memory_store` | 決定 6。管理画面のキャッシュ用途はほぼ無く、インスタンス間で共有しなくてよい |
| solid_queue | **外す**。gem、`config/queue.yml`、`config/recurring.yml`、`db/queue_schema.rb`、`bin/jobs`、`puma.rb` の `plugin :solid_queue` を削除。`config.active_job.queue_adapter = :async` | 決定 5。自前のジョブは無い（結果取り込みを作らないため）。残るのは Active Storage の解析・削除ジョブだけで、再起動で失っても実害が小さい |
| Neon 接続 | Cloud Run からは **プール接続用 URL**（Neon pooled） | インスタンス数 × スレッドで接続が溢れないようにする |
| Active Storage | 本番は R2（S3 互換）。開発は Disk。本番は **direct upload（presigned URL）**。R2 の公開 URL を builder が組み立てる | 決定 2。Rails 経由のアップロードにすると Cloud Run のリクエスト時間・メモリを使う |
| pnpm | ルート `pnpm-workspace.yaml` の `apps/*` は、admin に `package.json` が無い限り無視される。誤解防止に Task 1 で「admin は Rails のみ・JS パッケージにしない」と README / コメントに一言 | 任意だが運用ミス防止 |

**Interfaces（送る形）:**
- 受け取る: 開催回の PUT に `host: { loginId, passwordHash }`（省略可）。`passwordHash` は `pbkdf2-sha256$<反復回数>$<salt b64>$<hash b64>`（反復回数は 1〜100000 に制限）。`loginId` は `/^[A-Za-z0-9_-]{4,50}$/`。形式が違えば 422。
  - パスワードは**平文ではなくハッシュで受ける**。理由: PUT のボディが Worker のログやエラーに残ってもパスワードが読めない。ハッシュ生成は Rails（OpenSSL）、照合は Worker（WebCrypto `PBKDF2`）。
- 保存: DO の `ctx.storage.kv` に `"state"` とは別のキー `"host"` で保存する（`GameState`・ビューに載せないので、ゲストや投影画面に漏れない）。
- `POST /api/sessions/:id/host-login`: 認証ヘッダなし。DO に `loginId` / `password` を渡し、DO 内で照合する。
  - `loginId` の比較とハッシュ比較は定数時間（`safeEqual`）。ID 違いでもパスワード違いでも同じ 401。
  - **失敗回数制限**: 連続 10 回失敗で 60 秒ロック（DO の kv に回数と解除時刻を持つ。成功で 0 に戻す）。ロック中は 429。PBKDF2 は 1 回あたり CPU を使うので、ロック中は照合自体をしない。
  - 成功したら既存の `hostTokenFor(ADMIN_API_SECRET, sessionId)` を `{ token }` で返す。
- クライアント: `/host/:id` に入ったとき、URL の `?token=` も sessionStorage のトークンも無ければログインフォームを出す。ログイン成功で `token` を sessionStorage に保存し、以降は既存のフロー（WebSocket 接続）に合流する。

**既存トークンとの関係:**
- 幹事 HMAC トークンは**廃止しない**。WebSocket の認証は従来どおりトークンで、ID/パスワードは「トークンを受け取る入口」を足すだけ。`/ws/:id/host?token=` と `?token=` 付き URL は引き続き動く（`seed` / `loadtest` / 開発・緊急時の入口として使う）。
- Rails はトークンを計算も表示もしない（トークンは Worker がログイン成功時に返す）。
- 投影画面トークンはこの Task では**変えない**（「残る確認事項」参照）。

## 残る確認事項

決定済みの範囲では決めきれなかった点。推奨で進めてよいが、変えるなら着手前に。

1. **幹事パスワードの保管と表示**
   - **A（推奨）**: Rails が Active Record Encryption で暗号化して保存し、開催回詳細にいつでも表示する。口頭で伝え直せる。live には再 PUT できない（409）ので、忘れても作り直さずに済むようにする。暗号化鍵の管理が増える。
   - B: 作成直後の 1 回だけ表示し、Rails にはハッシュしか残さない。鍵管理は不要だが、忘れたら開催回ごと作り直しになる。
2. **投影画面トークン**
   - **A（推奨）**: 今のままの HMAC トークン URL。投影は読み取り専用で、機微な操作ができない。Rails が URL を作って詳細画面に出す。
   - B: 投影も ID/パスワードにする。幹事と同じ仕組みを使えるが、live の追加作業（投影側のログイン画面）と、運営が入力する手間が増える。
3. **ハッシュ方式とロック**
   - **A（推奨）**: PBKDF2-SHA256・反復 100000（Workers の上限）・salt 16 バイト。失敗 10 回で 60 秒ロック。
   - B: salt つき単純 SHA-256。実装は軽いが、ハッシュが漏れたときの総当たりに弱い。12 文字のランダムなら実用上は耐えるが非推奨。
4. **既存の幹事トークン URL を残すか**
   - **A（推奨）**: 残す。`seed` / `loadtest`・開発・緊急時の入口として使え、既存の WebSocket 認証も変えずに済む。トークンは `ADMIN_API_SECRET` を知る者しか作れない。
   - B: `host` が登録された開催回では `?token=` による幹事接続を拒否し、ID/パスワード経由だけにする。経路は 1 本になるが、`loadtest` の改修が要る。
5. **問題の画像を差し替えたときの R2 オブジェクト**
   - **A（推奨）**: 古いオブジェクトは消さない（スナップショットを使っている開催回の画像が消えないようにする）。R2 の容量は小さな増加に収まる。実装は Active Storage の既定の purge を止める。
   - B: 既定どおり消す。差し替え前の問題を取り込んだ開催回で画像が出なくなるので、当日までは画像を差し替えない運用が要る。
6. **live の変更（Task 6）を積む位置**
   - **A（推奨）**: `split-host-and-screen` の次の段として別 PR。
   - B: `split-host-and-screen` と同じ PR に含める（PR が大きくなる）。
